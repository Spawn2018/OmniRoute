## 1. DECYZJE

- „Robimy klona" Qargo (polecenie użytkownika), ale ChatGPT koryguje: kopiujemy model działania, UX i architekturę domenową, NIE kod, branding, logo, nazwy, grafiki, teksty dokumentacji, wygląd 1:1 (s. 15, 35).
- Order/pojazd/kierowca/trasa/dokument NIE są niezależnymi modułami — wspólny model domenowy zamiast „200 niezależnych modułów" (s. 2, 5).
- Order = jednostka przychodowa, Trip = jednostka kosztowa/wykonawcza; wiele orders w jednym tripie, jeden order z wieloma consignments/stages (s. 17).
- NIE kopiujemy Ant Design 1:1 — własny OmniRoute Design System (React+TS+GraphQL+Apollo+Zustand+Tailwind), „UI bardziej premium niż Qargo" (s. 29).
- Porzucamy Astro/statyczny HTML jako silnik aplikacji; Astro zostaje tylko dla omniroute.com (landing/docs/SEO), app.omniroute.com = prawdziwa aplikacja React (s. 35).
- Budujemy silniki, nie moduły po kolei: „Nie budowałbym 200 modułów po kolei. Budowałbym silniki, na których potem siedzi 200 modułów" (s. 36).
- OmniRoute będzie też dostawcą telematyki (decyzja użytkownika): TMS + FMS + telematics provider, ze sprzedażą sprzętu (s. 37–38, 53–54).
- Telematyka NIE jest modułem obok TMS — jest źródłem danych/systemem nerwowym całego systemu; dołożyć teraz, „zanim zabetonujemy model danych" (s. 38, 56–57).
- Architektura device-agnostic: Telematics Abstraction Layer zamiast zależności od jednego producenta; klient podłącza Geotab/Teltonika/Webfleet/GBox/Samsara/OEM albo kupuje OmniTrack (s. 42–43, 55).
- Reszta aplikacji NIE może wiedzieć, z jakiego urządzenia pochodzą dane — normalizacja do Unified Telemetry Model (s. 44, 60–61, 85–86).
- Telemetria jako eventy, nie `UPDATE vehicle` (s. 51–52).
- Routing: NIE kupujemy od razu HERE/TomTom na całą Europę — hybryda: warstwa darmowa (OSM+Valhalla+DATEX II/NAP), komercyjna (Urban Access Regulations), premium (TomTom traffic, HERE truck restrictions); TomTom jako premium fallback, nie podstawa (s. 61, 64–67).
- Nie budować biznesu na darmowym HERE (ograniczenia licencji dla asset management/telematics) (s. 66).
- Historyczny traffic: TAK, ale nie jako zamiennik live — trójwarstwowe ETA: Plan ETA (historia), Dynamic ETA (historia+live), Predictive ETA (AI) (s. 86–87). Live traffic dla dyspozytorów drobnicowych/spedytorów do monitoringu dostaw FIX (wymóg użytkownika, s. 86).
- ETA nie pokazuje „jednej magicznej godziny" — zakres + confidence (s. 88).
- Sterowanie chłodnią: TAK, ale nie „uniwersalny włącz/wyłącz" — zależne od capability konkretnego sprzętu; łańcuch vehicle→tracker→reefer→protocol→capability; read-only = przyciski zablokowane; AI nie steruje dowolnie (s. 93–94, 96–97).
- Prom NIE może być zwykłym stopem — specjalny obiekt FERRY_REST_EVENT (s. 98).
- ETA ma dwa poziomy: fizyczne vs prawne/operacyjne — „to są dwie zupełnie różne rzeczy" (s. 98–99).
- Aplikacja kierowcy NIE może być narzędziem do „poprawiania" tachografu — pełny audit trail każdej zmiany (s. 100).
- LLM ≠ źródło prawa; AI nie wymyśla prawa — decyzje z Legal Rules Database + oficjalne źródła + wersja; każda odpowiedź prowadzi do podstawy prawnej (s. 111).
- Zgodność prawna NIE jako jeden moduł — globalny Legal & Compliance Engine z hierarchią jurysdykcji i wersjonowaniem (s. 105–106).
- „100% zgodności" = cel architektoniczny, NIE obietnica produktowa; confidence score + eskalacja do prawnika (s. 113).
- Kosztów NIE przypisujemy do pojedynczego zlecenia — wielopoziomowy Cost Allocation Engine (potwierdzenie intuicji użytkownika, s. 114).
- Najpierw formalny model czasu (OMNI COMPLIANCE & TIME SIMULATION ENGINE), potem funkcje — inaczej ETA/ferry/tacho/FIX się rozjadą (s. 105).
- Użytkownik: to plan docelowy „po latach rozwoju" — nie kodować teraz (s. 105–106, 113).
- P&O: integrować tylko NOWE Freight API (stare API/EDI zastępowane od 1.06.2026) (s. 70).
- Ferry pricing: sprzedajemy z marżą, nie po cenie zakupu; klient nie widzi ceny zakupu (s. 74–75).

## 2. MODUŁY I FUNKCJE

- Przepływ główny Qargo: Order → Planning → Trip → Execution → Documents → Invoice → Analytics (s. 1).
- Select & Drop z walidacją AI: SELECT → AI CHECK → CAPACITY → TIME WINDOW → ADR → DRIVER HOURS → VEHICLE COMPATIBILITY → ROUTE → MARGIN → DROP; komunikaty typu „ORD-004 przekracza ładowność o 840 kg", „ORD-013 narusza okno dostawy" (s. 18–19).
- Mapa planistyczna: do 1000 nieplanowanych orders naraz; selekcja prostokątem/polygonem → popover z listą → plan selected (s. 6–7, 20–21).
- Email Intelligence pipeline: INBOX → EMAIL CLASSIFIER → DOCUMENT CLASSIFIER → ENTITY EXTRACTION → CUSTOMER MATCHING → LOCATION MATCHING → ORDER EXTRACTION → RATE EXTRACTION → CONFIDENCE SCORE → VALIDATION → ORDER DRAFT → AI APPROVAL → ORDER (s. 24). Docelowo AI czyta 600 maili/dzień, tworzy drafty, wylicza pricing, wysyła RFQ, sprawdza sankcje, przygotowuje do akceptacji człowieka (s. 32).
- Wycena z maila: „Gdynia → Oslo, 13 palet, 8,2 t, piątek" → ekstrakt → HISTORICAL RATES + CURRENT CARRIER RATES + FERRY + FUEL + TOLL + MARGIN POLICY → sugerowana cena €1 842 (s. 25).
- Document AI: OCR → CLASSIFY → EXTRACT → MATCH → VALIDATE → DIFF → TASK; diff per pole (MATCH/CONFLICT/NEW); alerty „waga CMR różni się o 380 kg", „dostawa 47 min poza oknem" (s. 25–26).
- AI Rule Builder: reguła z języka naturalnego → YAML (`when: destination_country: NO, cargo_value gt 10000, require cargo_insurance_confirmation`) → TEST na danych (1 842 orders: PASS 1 801, FAIL 41) → ACTIVATE (s. 26–27).
- Task Engine: EVENT → RULE ENGINE → TASK CREATED → ASSIGNED → DEADLINE → AI VALIDATION → ACTION → COMPLETE; auto-tworzenie wg trasy/towaru/service level/kategorii pojazdu/klienta/działu; przykład: order z krajem NO → task „Check customs documents" dla działu celnego (s. 27).
- AI Carrier Procurement: AI wybiera 25 przewoźników → wysyła zapytania → czyta odpowiedzi → ekstrahuje ceny → scoruje reliability → sprawdza capacity i sankcje → ranking (#1: cena €1 190, reliability 96%, OTD 97,2%, claims 0,4%, CO2 612 kg) (s. 28–29).
- Expected vs Actual: snapshot planowanego kosztu przed wykonaniem; przykład: plan marża 25,6% (€730), actual 16,1% (€460), variance +€270 kosztu (s. 23). AI Margin Guard: „fuel surcharge 6,4% poniżej rynku, oferta przewoźnika 11% powyżej mediany historycznej, prom +17%, sugerowana cena €3 184" (s. 23–24).
- Elektroniczna karta drogowa (z GBox): START TRIP → LOAD → DRIVE → REFUEL → WAIT → UNLOAD → COST → DOCUMENT → FINISH; składana z GPS+TACHO+CAN+FUEL+ORDER+DRIVER+STOPS+DOCUMENTS+EXPENSES — kierowca bez papierów (s. 39–41).
- Workflow geofence→billing: GeofenceEntered → STOP ARRIVAL → status ARRIVED → notyfikacja klienta → ETA=0 → task complete → timestamp → start licznika oczekiwania → po przekroczeniu darmowego limitu AI: „Potential waiting charge: €85" → CREATE COST → CREATE CUSTOMER SURCHARGE (s. 51–53).
- Ferry watchdog: ETA portu 18:02 vs cut-off 17:45 → „FERRY AT RISK" / „missed by 17 min" → AI: następny rejs, rebooking, nowe ETA, wpływ na tachograf i FIX, różnica kosztów, alternatywna trasa (s. 53, 76–77, 92).
- Cache tras: hash(origin+destination+vehicle+time); TTL: traffic 30–120 s, trasa 5–30 min, ograniczenia statyczne dni/tygodnie, LEZ do aktualizacji źródła (s. 67).
- ETA wagi dynamiczne: baza HISTORICAL 40% + LIVE 40% + TELEMATICS 20%; dobry live: 70/20/10; plan za 3 dni: Historical 70% + Calendar/season 20% + inne 10%; docelowo własne dane OmniRoute jako główne źródło (s. 88–89).
- FIX delivery (TIME-TO-FIX): FIX 14:00, arrival 13:18, bufor 42 min, prawdopodobieństwo 91% → SAFE; bufor 4 min/61% → AMBER; ETA 14:37 → RED; przyczyny rozbite: congestion +18, przerwa +45, ograniczenie +20, zgubiony prom +120 min (s. 89–90).
- Driver Time Solver: symuluje warianty A–I (regular rest, reduced daily rest, extension, split rest, ferry rest, ferry+interruption, weekly rest, multi-manning, alternative driver); optymalizuje czas/ryzyko/koszt/szansę FIX (s. 97).
- Fuel Fraud Detection: expected 8,2 vs actual 11,7 l/100 km → hipotezy: idling, kradzież, awaria czujnika, nietypowa trasa, korek (s. 48).
- Predictive maintenance: korelacja DTC + wzrost spalania + temperatura silnika + spadek mocy + wzorzec historyczny; „Vehicle 238 will require service in ~11 days based on mileage pattern" (s. 49, 94–95).
- Wirtualny doradca: odpowiedź liczona z systemu, np. „prawdopodobieństwo dotarcia przed 14:00: 87%" albo „legalny ETA 15:42; alternatywa: prom 18:30 + zmiana kierowcy → ETA 12:58" (s. 102).
- Tacho Office: codzienna analiza DDD+karta+GPS+CAN+wpisy manualne+bookingi promowe+zlecenia → raport naruszeń z wyjaśnieniem „odpoczynek rozpoczęty 37 min za późno; do uniknięcia postojem na parkingu A" (s. 101–102).
- Legal Feasibility Check przed przyjęciem zlecenia — przykład Gdańsk→Barcelona: DRIVER HOURS ⚠ tight, ADR ⚠, POSTING ⚠, REMUNERATION ⚠ France, DELIVERY 🔴 64%, wynik HIGH RISK (s. 111–112).
- Compliance & Time Simulation Engine: symulacja minuta po minucie: droga→korek→załadunek→jazda→przerwa→prom→boarding→odpoczynek na promie→zjazd→jazda→odpoczynek→weekend→rekompensata→FIX (s. 105).
