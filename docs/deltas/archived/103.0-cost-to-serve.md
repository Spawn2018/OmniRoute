## Wybrane / odrzucone / dlaczego

**Wybrane:** tabela `cost_to_serve` per tenant. Operator zapisuje, że ta wycena szła pod tą procedurą klienta (`customer_sop_id` + `quotation_id` + `source_ref`). Kwoty zostają na `quotation` / `charge`. Tablica 39.0 przestaje udawać, że filtr SOP+wycen to koszt obsługi. API składa: odczyt procedury, odczyt wyceny, zapis wiersza. Serwis kosztu obsługi nie importuje `parties` / `quotations` / `charges`. Wiele wierszy na jedną procedurę (kolejne wyceny). Unikat pary `(organization_id, customer_sop_id, quotation_id)`. Wzorzec jak S40. `get_quotation` już jest. `PartyService.get_sop` (odczyt po id, jak `get_review`) — repozytorium już ma `get_sop`. Migracja dokłada `uq_customer_sop_org_id` (FK tenanta).

**Łowca:** ISTNIEJE 39.0 `/cost-to-serve` + `customerSopsForParty` / `fetchQuotations` / `fetchParties` / `<Money/>`. ISTNIEJE 11.0 `customer_sop` (unikat org+party+code, nie org+id). ISTNIEJE 2.0 `quotation` z `uq_quotation_org_id`. BRAK tabeli `cost_to_serve` / ABC / stawki godziny. PODOBNE: 102.0 `cash_flow`; 101.0 `fx_difference`. Dwa joby (SOP vs koszt obsługi) = `/customer-sops` vs `/cost-to-serve`. Para `party`+wycena już siedzi na `quotation.party_id`.
