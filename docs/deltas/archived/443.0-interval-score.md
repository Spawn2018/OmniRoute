## Wybrane / odrzucone / dlaczego

- **Wybrane:** nowy BC `interval_score` — widok `security_invoker` + funkcja `IMMUTABLE` `interval_score(low, high, actual)` → `(mae, crps)` `Numeric(14,4)`. Złączenie: `outcome_ledger.suggestion_id = suggestion_ledger.id` oraz ten sam `organization_id`. Postgres liczy, Python nie (HC, VISION B.2).
- **Wybrane:** MAE = `abs(actual − (low+high)/2)`. CRPS = wzór zamknięty dla rozkładu jednostajnego na `[low, high]` (komentarz w migracji + test znanych trójek). `low = high` → CRPS = MAE = `abs(actual − low)`.
- **Wybrane:** tylko GET. Operator nie wpisuje metryki. Brak POST body `crps`/`mae`.
- **Wybrane:** nowy BC, nie `prediction_ledgers` — AGENTS tego BC **zakazuje** liczenia CRPS/MAE.
- **Odrzucone:** zmiana zapisu `prediction_ledger` (wpisane CRPS zostaje do domknięcia fali AI2).
- **Odrzucone:** Brier (brak prawdopodobieństwa na ledgerze) · champion/challenger / dryf (AI2.1) · FK `outcome_ledger` → `suggestion_ledger` · float · druga marża · SQL na `charge` · import serwisów ledgerów.

**Łowca:** PODOBNE `prediction_ledger` (193.0) — CRPS/MAE jako **wpis**. BRAK ścieżki liczonej ze złączenia. Nie klon drugiej tabeli z ręcznym CRPS.
