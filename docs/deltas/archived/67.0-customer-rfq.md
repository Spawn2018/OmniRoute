# Plaster 67.0 · S4 obiekt RFQ powiązany z wiadomością (M-28)

**Spec źródłowa:** [docs/PLAN-REALIZACJA.md](../../PLAN-REALIZACJA.md) § Kolejka S4  
**Zależy od:** 64.0 `inbound_message` · 65.0 `party_id` · 21.0 ślad `customer_inquiry` (zostaje tablicą)

**Status:** Zamknięty `/noc` 2026-09-03. Nie ślad wycen. Nie silnik wyceny. Nie IMAP. LLM nie liczy.

## Wybrane / odrzucone / dlaczego

**Wybrane:** jedna tabela `customer_rfq` per tenant, **jeden wiersz na wiadomość**. FK tenanta do `inbound_message` (`organization_id` + `inbound_message_id`). `source_ref` z wiadomości. Status `draft`. Operator na `/mail` tworzy RFQ z istniejącego wiersza. API składa BC; serwis RFQ nie importuje `inbound_messages` ani `quotations`. Panel 21.0 na `/quotations` zostaje śladem — nie zastępujemy go tą tabelą.

**Łowca:** ISTNIEJE: `inbound_message` (+ `party_id`), panel `customer_inquiry` (token UI, nie tabela). PODOBNE: `extraction_draft` korelacja `source_ref`; `inbound_message.party_id` jako FK tenanta. BRAK: tabela zapytania, FK do wiadomości, silnik wyceny na RFQ (S5).

**Odrzucone:**

- Ślad wycen / grupowanie `quotation` (to 21.0, nie S4).
- `INSERT` wyceny / silnik M-21 (S5).
- Kwoty, marża, `charge`, HS/CN na RFQ (S7).
- Auto-RFQ przy INSERT fixture wiadomości.
- Import `quotations` / `inbound_messages` w serwisie RFQ.
- IMAP / Graph / send.
- F9.1.

## Zakres

1. Migracja `customer_rfq`: `organization_id`, RLS FORCE, `inbound_message_id`, `source_ref`, `status = draft`, timestamps/`created_by`. Unikat `(organization_id, inbound_message_id)`. `uq_inbound_message_org_id` na `inbound_message`, żeby FK złożone miało nośnik.
2. `GET/POST /customer-rfqs` — `can_manage_customer_rfqs` = member; 403 bez tuple. POST bierze `inbound_message_id`; serwer kopiuje `source_ref` (i `party_id` jeśli wiadomość już ma).
3. `/mail`: przycisk „Utwórz RFQ”; lista `rfq_id` przy wiadomości. Zero nowego ekranu.
4. Test: wiadomość tenanta A nie wchodzi w RFQ tenanta B; drugi RFQ na tę samą wiadomość = błąd; brak kwoty w API.
