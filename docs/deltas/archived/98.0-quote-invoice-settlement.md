## Wybrane / odrzucone / dlaczego

**Wybrane:** tabela `quote_invoice_settlement` per tenant. Operator zapisuje, że ta faktura rozlicza tę wycenę (`quotation_id` + `sales_invoice_id` + `source_ref`). Kwoty zostają na `charge`. Tablica 34.0 przestaje udawać, że para `rate_line_id` + `sell` to rozliczenie. API składa: odczyt wyceny, odczyt faktury, zapis wiersza. Serwis rozliczenia nie importuje `quotations` / `sales_invoices` / `charges`. Wiele wierszy na jedną wycenę (zaliczka i reszta). Unikat pary `(organization_id, quotation_id, sales_invoice_id)`. Wzorzec jak S34.

**Łowca:** ISTNIEJE 34.0 `/quote-invoices` + `quotationInvoiceSettlements` / `fetchCharges` / `sell_amount`. ISTNIEJE 96.0 `sales_invoice` na `shipment`. BRAK tabeli rozliczenia / `quotation_id` na `charge`. PODOBNE: 96.0 `sales_invoice`; 95.0 `edi_message`. Dwa joby (faktura vs rozliczenie) = `/invoices` vs `/quote-invoices`.

**Odrzucone:**

- Zostawić tablicę z `charge` — to fundament 34.0, nie żywe M-41.
- Kopia `sell` / `buy` / marży na wierszu rozliczenia — druga prawda obok `charge`.
- JS odejmujący `quotation.amount − sell_amount`.
- `quotation_id` na `charge` — zgadywanie schematu.
- Wymóg `shipment.quotation_id = quotation_id` w tym plasterze — leftover; operator podaje dwa istniejące ID.
- SQL-refresh `quote_invoice_match_rate` — leftover 10.0.
- Live HTTP. LLM liczący różnicę. F9.1. KSeF (zrobione w 97.0, nie tu).
