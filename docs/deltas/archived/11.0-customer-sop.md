## Ustalenia

- Żywy ID: **M-16**. Token: `customer_sop` (GLOSSARY). Archiwum: obiekt `customer_sop`; funkcje pełnego modułu (reguły→zadania, walidacja zlecenia, wersje) — w 11.0 jako **katalog + zatwierdzenie**, nie pipeline.
- Unikat `(organization_id, party_id, code)`. FK złożone do `party`.
- `code`: po normalizacji jak sieć — `a-z`, potem `a-z0-9_`, długość 2–32. Puste / spoza wzorca = `InvalidCustomerSop`.
- `title` wymagany (1–128). `body` wymagany tekst, niepusty po trim, max 8000 znaków.
- `status`: `draft` | `approved`. Nowy wiersz = `draft`. `approve` tylko z `draft`; już zatwierdzone = `CustomerSopAlreadyApproved`.
- `approved_at` timestamptz NULL na draft, NOT NULL na approved.
- `source_ref` obowiązkowy; ręczny wpis = `tenant:manual`. Klient **nie** wysyła `source_ref` (`extra=forbid`).
- Nieznany `party_id` = `UnknownParty`. Nieznana SOP = `UnknownCustomerSop`. Konflikt kodu = `CustomerSopConflict`.
- `resolve(party_id, code)` dokładne po kodzie, nie luźny tytuł.
- OpenFGA: `can_manage_parties` = member. Brak nowej relacji, brak tuple na wiersz.
- RLS FORCE + test izolacji dwóch organizacji.
- Job operatora: `/customer-sops` — DataTableShell, dodanie (party_id + kod + tytuł + treść), zatwierdzenie. `/parties` — panel listujący SOP wybranego kontrahenta.
- import-linter: bez nowego pakietu. Extraction / quotations / charges / rate_lines / networks nie importują `parties`.
- Migracja `022_customer_sop_rls` (w górę i w dół).
- Kwoty i marża nie mieszkają na SOP. LLM nie liczy i nie pisze treści.
- `just dup` ≤ 3% — własny formularz (nie `CatalogCreateForm`: tu jest `body` + status, nie `aliases`).

## Schemat

`customer_sop`: `id`, `organization_id`, `party_id`, `code`, `title`, `body`, `status`, `approved_at`, `source_ref`, timestamps.
