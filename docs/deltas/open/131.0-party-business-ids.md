# Plaster 131.0 · M10-1 identyfikatory biznesowe `party` (M-10)

**Spec źródłowa:** [docs/spec/parties.md](../../spec/parties.md) · [docs/PLAN-REALIZACJA.md](../../PLAN-REALIZACJA.md) § M10-1 · [karty-pol-fala-o.md](../../analysis/karty-pol-fala-o.md) § M10-1
**Zależy od:** 5.0 `party` · 0.3 RLS · 0.4 OpenFGA
**Status:** Plan zaakceptowany `/noc` 2026-09-08. Ten sam żywy ID **M-10**. Nie F9.1.

## Wybrane / odrzucone / dlaczego

**Wybrane (węższe z kolejki M10-1):** kolumny `eori` i `duns` na **istniejącym** `party`. `vat_eu` już jest — dodać unikat i zapis. Każdy z czterech tokenów (`tax_id`, `vat_eu`, `eori`, `duns`) po normalizacji ma unikat częściowy `(organization_id, token)`. Nowy INSERT wymaga **co najmniej jednego** ID biznesowego. Rola `customer` dodatkowo wymaga `tax_id` (zakaz B2C bez NIP — bez nowej kolumny „osoba fizyczna”, bo to M10-2). Duplikat = `PartyConflict` → HTTP **409** z `existing_party_id` i `href` `/parties/{id}`. Job na tym samym `/parties`. Zero nowej tabeli.

**Łowca:** ISTNIEJE 5.0 `party.tax_id` / `vat_eu` + `normalize_tax_id` + unikat `(org, country, tax_id)` + `create_party` (dziś `vat_eu` nie zapisuje) + `POST /parties` + UI `/parties` + `can_manage_parties`. Conflict dziś leci jako `InvalidPartyData` (400). BRAK `eori` / `duns`. BRAK unikatów `vat_eu`. PODOBNE: `ChargeCodeConflict` — nowy `PartyConflict` z linkiem, nie drugi katalog.

**Odrzucone:**

- Nowa tabela `party_identifier` / EAV — karta mówi kolumny na `party`; trzecia tabela bez powtórzenia.
- `party_role_assignment`, `is_sole_trader`, `parent_party_id` — to **M10-2**.
- Backfill i `NOT NULL` na starych wierszach — zmyślałoby NIP.
- Zmiana wszystkich `*Conflict` na 409 — poza M10-1; tylko `PartyConflict`.
- Live GUS/VIES, merge duplikatów, resolve po EORI/DUNS, nowa relacja OpenFGA.
- ExtractionService zapisujący `party`. LLM, kwota, marża.

## Zakres

1. Migracja `074_party_business_ids`: `eori` / `duns` TEXT NULL. Unikaty częściowe `(organization_id, vat_eu|eori|duns)` gdy nie NULL. Istniejący unikat `tax_id` zostaje (org+kraj+token). RLS z 015 — nie nowa tabela.
2. Domenowe `normalize_vat_eu` / `normalize_eori` / `normalize_duns`. `require_business_id`. `customer` bez `tax_id` → `InvalidPartyData`.
3. `PartyService.create_party`: przyjmuje `vat_eu` / `eori` / `duns`; przed INSERT szuka po każdym podanym tokenie; trafienie → `PartyConflict`. `IntegrityError` → ten sam konflikt (drugi lookup).
4. Handler HTTP: `PartyConflict` → 409 `{ detail, existing_party_id, href }`. Inne `DomainError` bez zmiany.
5. UI `/parties`: pola VAT UE / EORI / DUNS; kolumny; 409 pokazuje link do istniejącego wiersza. `SHIPPED_CHARGE_ROUTES["131.0"]` = `/parties`.
6. `just api-types`. GLOSSARY: `eori`, `duns`. How-to w `katalogi.md`.

## Poza zakresem

M10-2 role/JDG/parent · B0a · O1–O8 · live GUS/VIES · merge · resolve po EORI · portal · F9.1

## Ustalenia

- Tokeny: `tax_id`, `vat_eu`, `eori`, `duns`. Normalizacja: NIP jak dziś; pozostałe = trim + uppercase, bez spacji; DUNS = same cyfry, 9 znaków.
- Stare wiersze: ID-e nullable. Nowy INSERT bez żadnego z czterech → 400. `customer` bez `tax_id` → 400 nawet gdy jest EORI/DUNS.
- 409 tylko gdy token już stoi w **tym** tenancie. Cudzy tenant = RLS, nie link.
- OpenFGA: `can_manage_parties`. Brak nowej relacji.
- LLM nie liczy. `charge` zostaje prawdą o marży.

## Schemat

`party.eori` String(32) NULL. `party.duns` String(16) NULL. `party.vat_eu` bez zmiany typu.
