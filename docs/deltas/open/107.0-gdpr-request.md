**Spec źródłowa:** [docs/spec/gdpr.md](../../spec/gdpr.md) · [docs/PLAN-REALIZACJA.md](../../PLAN-REALIZACJA.md) § Kolejka S45  
**Zależy od:** 46.0 `/gdpr` · 0.3 `app_user` · 0.4 OpenFGA

**Status:** Zaakceptowany `/noc` 2026-09-03. Ten sam żywy ID **M-56**. Nie F9.1.

## Wybrane / odrzucone / dlaczego

**Wybrane:** tabela `gdpr_request` per tenant. Operator na `/gdpr` **zapisuje** wniosek (`access` albo `erasure`) wobec istniejącego `app_user`, potem **wypełnia**. Wypełnienie `access` = status `fulfilled` (inwentarz 46.0 **jest** udostępnieniem — bez ZIP). Wypełnienie `erasure` = API składa: `TenancyService` ustawia tombstone na koncie (`email`, `display_name`, `password_hash = NULL`) **i** status wniosku `fulfilled`. Wiersza `app_user` nie kasujemy (`created_by` w innych tabelach). Serwis wniosków nie importuje `tenancy` i nie zapisuje `app_user`. `SHIPPED_CHARGE_ROUTES["107.0"]` = `/gdpr`. OPS_JOBS długość 50.

**Łowca:** ISTNIEJE 46.0 `/gdpr` + `gdprSubjects` + `fetchTenancyUsers` + `TenancyService.get_user`. BRAK tabeli `gdpr_request` / `erasure` / endpointu usuwania. PODOBNE: 74.0 `operator_decision` (status, nie kasuje źródła); 97.0 druga akcja na tym samym ekranie. Dwa joby (inwentarz vs wniosek) = jeden ekran, druga akcja.

**Odrzucone:**

- `DELETE` wiersza `app_user` — łamie FK `created_by`.
- Kasowanie `inbound_message` / `party` / `extraction_draft` / `charge` — inny BC, nie ten job.
- DPIA, zgody, portal osoby, M-54/M-55 (brak żywej nazwy w PLAN).
- ZIP / plik eksportu / LLM klasyfikujący rodzaj wniosku.
- Nowa trasa — OPS_JOBS ma zostać długości 50.
- F9.1.

3. UI `/gdpr`: inwentarz 46.0 zostaje; lista wniosków + zapis + „Wypełnij”. `data-gdpr="board"` zostaje. Asercja 46.0 „bez tabeli erasure” schodzi. `SHIPPED_CHARGE_ROUTES["107.0"]` = `/gdpr`. OPS_JOBS = 50 (job RODO: wniosek i usunięcie katalogu).
4. Test izolacji. `just api-types`. How-to `docs/operator/rodo.md`.

## Ustalenia

- Token: `gdpr_request` (tabela). UI zostaje `gdpr`. How-to: `rodo.md`.
- `request_kind`: `access` | `erasure`. `status`: `open` | `fulfilled`.
- `source_ref`: `fixture://gdpr-request/` albo `tenant:manual`. Pusty po trim = 400. Max 256.
- Tombstone erasure: `email = erased.{app_user_id.hex}@erased.invalid` (musi przejść `EmailStr` na GET users), `display_name = usunięte`, `password_hash = NULL`. Ten sam UUID → ten sam email (powtórne wypełnienie nie psuje uniku).
- Unikat częściowy: jeden `open` na `(organization_id, app_user_id, request_kind)`.
- Serwis wniosków bez `httpx` / bez importu `app.services.tenancy`. ExtractionService nie importuje wniosków.
- LLM nie liczy i nie nadaje kind. HITL extract bez zmian. `charge` zostaje prawdą o marży.
- Formularz: `data-gdpr="request-form"` + `flex flex-col gap-2`. Nie `CatalogCreateForm`, nie `inline-flex` z 105.0, nie `SopQuoteStack`.
- OPS_JOBS zostaje długości 50.

## Schemat

`gdpr_request` (nowa): `id`, `organization_id`, `app_user_id`, `request_kind`, `status`, `source_ref`, timestamps, `created_by`. FK tenanta do `app_user`. Brak kolumny email na wniosku (kopia PII po erasure = błąd).
