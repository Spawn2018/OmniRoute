# Plaster 10.0 · M-13 Karta wyników kontrahenta (`party_scorecard`)

**Spec źródłowa:** [docs/spec/party-scorecard.md](../../spec/party-scorecard.md)  
**Zależy od:** 5.0 `party` · 0.4 OpenFGA · 0.6 DataTableShell · 5.1 `quotation.party_id` (czytanie **nie** w tym plasterze)

**Status:** Plan `/noc` 2026-09-02. Nie Fala 8. Nie M-14.

## Wybrane / odrzucone / dlaczego

**Wybrane (węższe z M-13):** jedna bieżąca karta per kontrahent — tabela `party_scorecard` ze snapshotem wskaźników (Decimal, nie float). Operator zapisuje kartę ręcznie (`source_ref` = `tenant:manual`). Lista rankingowa sortuje istniejące karty — to powierzchnia „kieruj zapytanie do najlepszych”, **bez** wysyłki RFQ. Żywy ID **M-13**. Ten sam BC `app.services.parties` (jak `party_contact` / 8.0) — nie drugi serwis.

**Odrzucone:**

- Silnik liczący `response_rate` / medianę z `quotation` — wycena 5.1 nie ma znaczników odpowiedzi ani RFQ (to M-30). Formuła z niepełnych danych = zgadywanie.
- `quote_invoice_match_rate` z faktury — M-40/M-41 nie istnieją. Kolumna snapshotu wolno; wyliczenie = leftover.
- Pozycja cenowa **per relacja** (lane POL/POD) — osobne ziarno; 10.0 = jedna karta na `party`. Lane = leftover.
- Automatyczny credit scoring `natural_person` / JDG — **M-14 + AI Act**. `party` nie ma `legal_form`; 10.0 tego nie dokłada i nie czyta `credit_limit` jako scoringu.
- Nadpisanie M-10 `party`, M-08 `charge`, M-11 `resolve_email`, M-12 `network`.
- LLM / ExtractionService liczące wskaźniki. Routing zapytań (M-30). Scraping sieci. Portal. Auth0. M-02.

## Zakres

Snapshot karty wyników per tenant+`party`. Lista (ranking), odczyt po `party_id`, zapis/upsert. RLS FORCE. OpenFGA `can_manage_parties` (bez nowej relacji). UI: ranking `/party-scorecards` + panel na `/parties`.

## Ustalenia

- Żywy ID: **M-13**. Token: `party_scorecard` (GLOSSARY). Archiwum: obiekt `party_scorecard`; funkcje pełnego modułu (odpowiedź, mediana, pozycja cenowa, zgodność oferty z fakturą, rollover, kierowanie) — w 10.0 jako **kolumny snapshotu**, nie jako pipeline.
- Unikat `(organization_id, party_id)` — jedna bieżąca karta. FK złożone do `party(organization_id, id)` jak `party_contact`.
- Wskaźniki udziałowe: `Numeric(7,4)`, zakres `[0, 1]`, NULL = nieznany. Nie procent float. Nie Python do aggregatów „na przyszłość”.
  - `response_rate` — wskaźnik odpowiedzi
  - `median_response_hours` — `Numeric(12,4)`, `>= 0`, NULL = nieznany
  - `price_position` — pozycja cenowa (0 tanio … 1 drogo względem rynku tenanta); w 10.0 na karcie partii, nie na lane
  - `quote_invoice_match_rate` — zgodność oferty z fakturą (snapshot; wyliczenie M-40)
  - `rollover_count` — `Integer >= 0`, NULL = nieznany
- `sample_size` `Integer >= 0` NOT NULL default 0; `window_days` `Integer > 0` NOT NULL default 90; `computed_at` timestamptz NOT NULL przy zapisie.
- `source_ref` obowiązkowy; ręczny wpis = `tenant:manual`; fixture = `party_scorecard:<party_id>`. Klient **nie** wysyła `source_ref` (`extra=forbid`).
- Nieznany `party_id` przy zapisie = `UnknownParty`. Brak karty przy GET = `UnknownPartyScorecard`. Zły zakres wskaźnika = `InvalidPartyScorecard`.
- OpenFGA: istniejące `can_manage_parties` = member. Brak tuple na wiersz.
- RLS FORCE + test izolacji dwóch organizacji.
- Job operatora: `/party-scorecards` — DataTableShell, ranking (`response_rate` DESC NULLS LAST, potem `median_response_hours` ASC NULLS LAST). `/parties` — panel karty (podgląd + zapis snapshotu) przy znanym `party`.
- import-linter: bez nowego pakietu. Extraction / quotations / charges / rate_lines / networks / commodity_codes / nbp_rates / dangerous_goods nie importują `parties`.
- Migracja `021_party_scorecard_rls` (w górę i w dół).
- Kwoty i marża nie mieszkają na karcie. `charge` zostaje prawdą o marży. LLM nie liczy.
- `just dup` ≤ 3% — panel na `/parties` i ranking jak katalog 5.2, nie klon całego `CatalogCreateForm` jeśli pola nie są `code`/`name`/`aliases`.
