# Plaster 14.0 · M-14 Ocena kredytowa (`credit_review`)

**Spec źródłowa:** [docs/spec/credit-review.md](../../spec/credit-review.md)  
**Zależy od:** 5.0 `party` / `credit_limit` (nie nadpisuj) · 10.0 `party_scorecard` (nie mieszaj) · 0.4 OpenFGA · 0.6 DataTableShell

**Status:** Plan `/noc` 2026-09-02. Nie Fala 8. Nie auto-scoring. Nie M-08 `charge`.

## Wybrane / odrzucone / dlaczego

**Wybrane (węższe z M-14):** katalog recenzji kredytowej — tabela `credit_review` (kontrahent + dzień + decyzja operatora + notatka). Operator zapisuje, co uzgodnił z księgowością / ubezpieczycielem. Żywy ID **M-14**. Token: `credit_review`. Ten sam BC `app.services.parties` (jak `party_scorecard` / 10.0) — nie drugi limit na `party`, nie `credit_score`.

**Łowca:** BRAK `credit_review`. ISTNIEJE: `party.credit_limit` + `credit_currency` (5.0, para ręczna, nie scoring). PODOBNE: `party_scorecard` (snapshot wskaźników, zakaz scoringu osoby).

**Odrzucone:**

- Automatyczny credit scoring `natural_person` / JDG — **zakaz AI Act** (PLAN). `party` nie ma `legal_form`; 14.0 tego nie zgaduje i nie dokłada PESEL. Brak pola score = brak silnika, nie teatr „score = 0”.
- Nadpisanie `credit_limit` — 5.0 to ręczny limit Decimal. Recenzja ≠ nowy limit. Zmiana limitu zostaje na `/parties`.
- HTTP do BIK/KRD/GUS credit — brak sekretów tenanta (leftover HC), jak live HTTP w 13.0.
- Mieszanie z `party_scorecard` — karta to odpowiedź/cena, nie kredyt.
- SQL z `quotation`/`charge` — brak faktury (M-40) i znaczników RFQ (M-30).
- M-15 VDF. LLM liczący limit. Portal. Auth0. M-02.

## Zakres

Katalog recenzji per tenant+`party`+dzień. Lista, odczyt, dodanie, `resolve` as-of. RLS FORCE. OpenFGA `can_manage_parties`. UI: `/credit-reviews` + panel na `/parties`.

## Poza zakresem

Auto-scoring · biuro kredytowe · `legal_form` · PESEL · scoring osoby/JDG · zapis `credit_limit` · M-15 · ExtractionService→parties · LLM liczący kwotę

## Ustalenia

- Żywy ID: **M-14**. Token: `credit_review` (nowy w GLOSSARY). Archiwum: ocena kredytowa; w 14.0 jako **katalog recenzji**, nie silnik scoringu.
- Unikat `(organization_id, party_id, review_date)`.
- FK złożone do `party(organization_id, id)`.
- `decision`: dokładnie `ok` | `hold` | `refuse` (trim, lower). Inne = `InvalidCreditReview`.
- `note` opcjonalny po trim, max 512; pusty → NULL.
- Brak kolumny score / rating / probability — świadomy zakaz, nie leftover „dodamy float później”.
- `source_ref` obowiązkowy; ręczny wpis = `tenant:manual`. Klient **nie** wysyła `source_ref` (`extra=forbid`).
- `resolve(party_id, on_date)`: SQL `review_date <= on_date` ORDER BY `review_date` DESC LIMIT 1; pusto = `UnknownCreditReview`. Nieznany `party` = `UnknownParty`. Konflikt dnia = `CreditReviewConflict`.
- OpenFGA: `can_manage_parties` = member. Brak nowej relacji. Nie `can_manage_charges`.
- RLS FORCE + test izolacji dwóch organizacji.
- Job operatora: `/credit-reviews` — DataTableShell, dodanie (party_id + data + decyzja + notatka), resolve. `/parties` — panel recenzji wybranego kontrahenta (jak SOP / karta). Limit z `party` tylko do odczytu.
- import-linter: bez nowego pakietu `app.services.*` — zostaje `parties`. Extraction nie importuje `credit_review`.
- Migracja `025_credit_review_rls` (w górę i w dół).
- `just dup` ≤ 3% — własny formularz (nie `CatalogCreateForm`).
- LLM nie liczy. `charge` zostaje prawdą o marży.
