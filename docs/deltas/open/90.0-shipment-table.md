## Wybrane / odrzucone / dlaczego

**Wybrane:** jedna tabela `shipment` per tenant (= default arch. M-89). Operator **zapisuje** zlecenie z istniejącej wyceny z `party_id`. Jeden wiersz na wycenę. API składa BC: odczyt `quotation`, zapis `shipment`. Serwis zlecenia nie importuje `quotations` / `charges` / `operator_decisions`. Tablica 28.0 przestaje udawać, że wycena to zlecenie. Wzorzec jak S4 (`customer_rfq` z wiadomości).

**Łowca:** ISTNIEJE 28.0 `/shipments` + `data-shipment="board"` + `fetchQuotations` / `quotationAcceptancePending` + `quotation.party_id`. BRAK tabeli `shipment` / `shipment_leg` w modelach i Alembic. PODOBNE: 67.0 `customer_rfq` (FK tenanta + unikat na źródle); 83.0 `carrier_inquiry` (`status = draft`, `source_ref`). Dwa joby (oferta vs zlecenie) = dwa ekrany (`/quotations` vs `/shipments`), **nie** dwie tabele.

**Odrzucone:**

- Druga tabela `booking` (arch. M-89) — PLAN: dwa obiekty tylko przy dwóch jobach; tu jeden job zapisu zlecenia.
- Auto-INSERT przy Przyjmij (S11) — świadomy zapis operatora, nie skutek uboczny decyzji.
- Bramka „tylko accepted” / import `operator_decisions` — leftover; S24 zostaje na `/quotations`.
- Kwoty, marża, kopia `charge` na zleceniu — prawda zostaje w `charge`.
- Numer `GD/2026/…` / licznik / LLM nadający numer — S8 leftover.
- `shipment_leg`, tracking (S29), dokumenty (S30), wyjątki (S31), EDI, SOP przy zapisie, bramka sankcji/kredytu.
- Live HTTP, Temporal, outbox, F9.1.
