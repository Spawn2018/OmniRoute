# Plaster 4.1 · M-05 Geografia (`location` + strefy taryfowe)

**Spec źródłowa:** [docs/spec/geography.md](../../spec/geography.md), sekcja 4.1  
**Zależy od:** 0.3 RLS · 0.4 OpenFGA · 0.6 DataTableShell · 4.0 `port` (FK `kind = 'unlocode'`)

**Status:** Plan zaakceptowany 2026-09-01. Kod dopiero w `/plaster`, nowa rozmowa, tryb Agent.

## Zakres

Tabela `location` (`unlocode` | `postal_zone` | `address`) oraz `location_zone_member` — zakresy kodów pocztowych składające się na strefę taryfową tenanta. Strefa konfigurowalna per organizacja: żaden tenant nie widzi ani nie dziedziczy cudzego podziału. `resolve` kodu pocztowego do strefy w Postgresie. UI `/locations`.

## Poza zakresem

`terminal` i World Port Index (4.2), geometria poligonowa i OSM, strefy czasu dojazdu, ISPS, FK do `party`, POL/POD w `quotation`, podpięcie `rate_line`, `pg_trgm`, Q2 M-10, M-02 outbox, Auth0, Exit Wave FE, leftovery UI ADR-0003.

## Ustalenia

- Żywy ID modułu: **M-05**, bez zmian po 4.0. Brak kolizji z żywym M-07 `rate_line` / M-08 `charge`.
- Strefa taryfowa **nie ma własnej tabeli** — to wiersz `location` z `kind = 'postal_zone'`. Dwie tabele, zgodnie ze spec.
- Rodzaje w 4.1: `unlocode`, `postal_zone`, `address`. `terminal` wchodzi dopiero w 4.2.
- `kind = 'unlocode'` wiąże się z 4.0 przez FK `(organization_id, port_id)` → `port(organization_id, id)`, nie przez luźny tekst. Kolumna złożona, żeby baza odrzuciła wskazanie portu innego tenanta.
- Zakres pocztowy: `country_code` + `postal_from`/`postal_to` jako znormalizowany tekst (bez spacji i myślników, upper). Porównanie leksykograficzne przy stałej długości w obrębie kraju — jeden mechanizm dla PL `81198`, DE `20095` i alfanumerycznych GB/NL/CA.
- Kraj siedzi na wierszu członkowskim, nie na strefie: strefa taryfowa bywa wielokrajowa.
- Nakładanie zakresów jednego tenanta **zakazane przez bazę**, nie przez walidację w serwisie:

  ```sql
  CREATE EXTENSION IF NOT EXISTS btree_gist;
  CREATE TYPE postal_range AS RANGE (subtype = text, collation = "C");

  ALTER TABLE location_zone_member ADD CONSTRAINT ex_zone_member_no_overlap
    EXCLUDE USING gist (organization_id WITH =, country_code WITH =, postal_span WITH &&);
  ```

- Kolacja `"C"` jest warunkiem poprawności, nie stylem: domyślna kolacja PL/DE sortuje inaczej niż bajtowo i zakresy przestałyby się domykać.
- `organization_id WITH =` w constraincie — exclusion patrzy poza RLS, więc bez tego wiersz jednego tenanta blokowałby zapis drugiemu.
- `postal_span` jako kolumna generowana z `postal_from`/`postal_to`. Jeśli konstruktor własnego typu nie przejdzie jako immutable, fallback: zwykła kolumna ustawiana w repozytorium przy zapisie. Rozstrzygnięcie w `/plaster`.
- `resolve(country_code, postal_code)` liczony w Postgresie (zasada 11): `WHERE postal_span @> :code AND length(postal_from) = length(:code)`. Warunek długości jest niezbędny — bez niego `811989` wpada leksykograficznie w zakres `[81000, 81999]`.
- Brak trafienia = wyjątek domenowy z `domain/errors.py`, nie `None` i nie luźny string. Wzorzec odrzutu jak `resolve` portu w 4.0.
- `zone_location_id` przez FK `(organization_id, zone_location_id)` → `location(organization_id, id)`. Wymóg `kind = 'postal_zone'` egzekwuje serwis — CHECK nie sięga innej tabeli, a trigger byłby drożdżą pod jedną regułę.
- OpenFGA bez zmian: `can_manage_geography` = `member`, jedna relacja na 4.0–4.2, już w `authz/model.fga`.
- RLS FORCE na obu tabelach + test izolacji dwóch organizacji. Runtime `omniroute_app` NOBYPASSRLS.
- `source_ref` obowiązkowy na obu tabelach; strefy tenanta = `tenant:manual`.
- Job operatora w tym plastrze: `/locations` (DataTableShell) — lista lokalizacji, panel strefy z zakresami, pole resolve kodu pocztowego.
- Brak istniejącej implementacji do ponownego użycia: skan `backend/app` nie znalazł ani `location`, ani stref pocztowych (trafienia to `timezone` w `base.py` i `refresh_token.py`). Nic nie duplikujemy.
- `backend/app/services/geography/AGENTS.md` trzyma dziś `location` na liście **Zakaz** („4.1 / 4.2”). Plaster musi przenieść `location` do dozwolonych zależności i dopisać `app.models.location` — inaczej kontrakt BC kłamie po merge'u. `terminal` i WPI zostają w zakazie do 4.2.

## Schemat

`location`: `id`, `organization_id`, `kind`, `name`, `code` (krótki kod strefy, unikalny per tenant gdy nie NULL), `port_id`, `country_code`, `city`, `address_line`, `postal_code`, `lat`/`lng` Numeric, `source_ref`, timestamps. CHECK per `kind`: `unlocode` wymaga `port_id` i zeruje pola adresowe; `postal_zone` wymaga `code` i zeruje `port_id`; `address` wymaga `country_code`, `city`, `address_line`. `UNIQUE (organization_id, id)` jako nośnik dla FK tenant-safe.

`location_zone_member`: `id`, `organization_id`, `zone_location_id`, `country_code`, `postal_from`, `postal_to`, `postal_span`, `source_ref`, timestamps. CHECK `length(postal_from) = length(postal_to)` oraz `postal_from <= postal_to`.
